# 포트폴리오 콘텐츠 작성/수정

이 스킬은 콘텐츠 작성 규칙과, 작성 후 품질 검수로 이어지는 흐름을 정의한다.
전체 구조는 레포 루트의 `CONTENT.md`가 이미 문서화하고 있으니 먼저 그걸 확인한다.

## 1. 어디를 고치는지 먼저 판단한다

| 바꾸려는 것 | 파일 |
| --- | --- |
| 사이트 전역 문구, 히어로, 섹션 라벨, 연락처, 푸터 | `src/data/siteContent.ts` |
| 프로젝트 소개 | `src/data/projects.ts` |
| 학력/연구실/컨퍼런스/경력 | `src/data/experience.ts` |
| 논문 | `src/data/publications.ts` |
| 블로그 포스트 | `src/content/posts/*.mdx` (새 글은 새 `.mdx` 파일 추가) |
| 레이아웃/색/타이포 | `src/index.css` — 이건 콘텐츠가 아니라 디자인 변경이므로 UI 작업 스킬(디자인 가이드) 영역 |

## 2. MDX 포스트 작성 규칙

새 포스트를 쓸 때 frontmatter는 기존 포스트(`src/content/posts/why-agentic-ai.mdx`)와
형식을 맞춘다:

```
---
title: "..."
date: "YYYY-MM-DD"
tags: ["...", "..."]
summary: "한 문장 요약"
---
```

- `date`는 반드시 `YYYY-MM-DD` 문자열
- `tags`는 배열, 소문자-kebab-case 권장 (기존 포스트의 태그 스타일과 맞춘다)
- 본문 톤: 1인칭, 기술적이되 담백하게. 과장된 마케팅 문구나 지나친 감탄사는 쓰지 않는다
  (기존 포스트가 취하는 "연구 과정을 담담하게 서술" 톤을 유지)
- 내부에서 프로젝트나 논문을 언급할 때는 `src/data/projects.ts` / `publications.ts`에
  실제로 존재하는 항목만 참조한다 — 존재하지 않는 걸 언급하면 QA 단계에서 걸러진다

## 3. 데이터 파일(`src/data/*.ts`) 수정 규칙

- 기존 항목의 필드 구조(타입)를 그대로 유지한다 — 임의로 필드를 추가/삭제하면
  해당 타입을 쓰는 컴포넌트가 깨질 수 있다 (`src/types` 확인)
- id/slug 값은 다른 파일에서 참조될 수 있으니, 기존 항목의 id를 바꿀 때는
  그 id를 참조하는 다른 파일이 있는지 먼저 검색한다

## 4. 작성 후 — content-qa 에이전트로 검수

**의미 있는 분량의 콘텐츠(새 포스트, 여러 항목 수정)를 작성/수정했으면**, 커밋하기 전에
`content-qa` 에이전트를 호출해 검수받는다:

```
Agent(subagent_type: "content-qa", model: "opus", prompt: "{바뀐 파일 경로들과 변경 요약}")
```

에이전트가 지적한 항목 중 실제 문제인 것만 반영한다 — 지적을 무조건 다 받아들이지 않고,
근거를 확인한다.

**사소한 변경(오탈자 한 줄 수정 등)에는 이 단계를 생략해도 된다.** 매번 강제하면 오히려
작은 수정에 과한 오버헤드가 된다 — 분량과 영향 범위로 판단한다.

## 5. 커밋

검수까지 끝났으면 `commit-and-push` 스킬로 넘어간다 (빌드 검증 → 커밋 → 사람 확인 → 푸시).

## 테스트 시나리오

- **정상 흐름**: "새 포스트 써줘" → 이 스킬로 MDX 작성 → content-qa 호출 → 지적사항 반영 → commit-and-push
- **에러 흐름**: content-qa가 "확인 불가"로 보고한 참조(예: 대상 프로젝트 데이터 파일 없음) →
  사람에게 그 항목의 존재 여부를 물어보고 진행 (추측으로 넘어가지 않음)
